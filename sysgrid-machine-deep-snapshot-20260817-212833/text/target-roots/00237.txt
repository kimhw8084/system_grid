## What v1.3.4 changes

### Mandatory Telegram progress delivery

- Installation discovers existing Telegram credentials from secure SysGrid config or environment variables. When absent, it prompts only for the hidden bot token, validates the bot with `getMe`, opens the bot conversation, and learns the numeric private-chat ID from one fresh `/start` message.
- Automatic discovery is refused when the bot has an active webhook, because Telegram does not allow `getUpdates` long polling while a webhook is configured; non-interactive and webhook-managed setups can provide a numeric `SYSGRID_TELEGRAM_CHAT_ID` directly.
- Credentials are stored only in a local `0600` configuration file and are never copied into qualification evidence, logs, or product artifacts.
- Installation sends a live Telegram probe before activation and repeats the probe from the exact installed supervisor bytes.
- Every numbered supervisor step emits one deduplicated Telegram message. Steps 1–3 fail closed before Stable Engine launch if mandatory delivery is unavailable.
- Long step 3 execution emits a bounded heartbeat every five minutes with elapsed time and run ID.
- Completion and failure messages include classification and runtime while preserving product evidence even if Telegram becomes unavailable after engine launch.

### Runtime observability

- `sgs` now shows live elapsed time, last Telegram heartbeat, Telegram configuration status, and the last engine runtime.
- The supervisor extracts only timing/classification metadata from verified engine evidence and appends it to a local immutable-style JSONL runtime history without altering the trusted ZIP.
- Runtime summaries include each recipe duration, exit code, timeout state, total engine duration, and failed stage.

### Existing convergence protections retained

- Exact live-engine reattachment after supervisor interruption.
- Verified completed-output recovery without product replay.
- One safe mutation retry only from complete exact pre-state proof.
- Replay refusal for post-state, unknown state, or ambiguity.
- Byte-identical Inbox duplicate convergence.
- Complete canonical diagnostic ZIP on platform failure.

### Existing safety and performance retained

- One non-blocking kernel lock.
- Exact engine SHA-256 and self-test.
- Complete capsule and package manifest coverage.
- Strict ZIP safety, CRC, decompression, and executable-member defenses.
- Canonical `.txt`, GNU-style `.sha256`, and JSON state-ledger compatibility.
- Resource-aware concurrent independent preflight with complete aggregate reporting.
- Content-addressed, SHA-verified, fsynced, atomic evidence publication.

## Performance boundary

The supervisor maximizes safe platform concurrency and exports detected CPU/memory capacity as resource hints. The immutable capsule and Stable Engine remain authoritative for product-test ordering and parallel test workers. The supervisor cannot safely invent new tests, skip gates, force-apply a patch, or replay an ambiguous mutation.

The intended useful outcomes are:

1. **PASS:** all declared product gates complete and delivery succeeds.
2. **Application findings:** the complete trusted test matrix returns review-ready product defects.
3. **Rare trust stop:** continuing would risk wrong or duplicate product mutation; one diagnostic ZIP is produced for exact recovery.
